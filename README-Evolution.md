# README Evolution

## 2026-09-15 · 从 Experience 归并转向 Run 归档与独立笔记

- 发生：用户根据实际使用反馈，认为构造和维护 E 增加复杂度，提出仅保留 Run，另建 pi-note。用户明确笔记入口是目录根部的全部笔记，而非 Agent 先前建议的单一索引页；以 `description` 和 `open` 控制默认展示。随后邀请讨论工具和其余逻辑，并提出可另开 pi-experiencev2 目录。
- 分析：旧版同时承担事实归档、知识组织与上下文管理。E 的父子关系、来源归并、计划提交、backlog 和整理提醒将知识提炼变成了必须维护的结构。独立笔记能够承载可修改认知，但是否继续按 Run 管理当前上下文，仍是需要单独决定的产品边界。用户尚未确认新的工具清单、折叠容量策略或迁移方案。
- 改变：在新目录保存设计草案，区分已确认方向与建议。建议移除 `get_experience`、`prepare_experience`、`compose_experience`，将 `search_memory` / `delete_memory` 改为 Run 专用操作；将综合 `get_memory_status` 的目录职责归入 `list_runs`，诊断职责归入用户面板。E 来源索引、父关系、归并计划及过期检查、未沉淀状态、自动整理资格、5k 概览整理提醒及 `/experience prepare` 不再属于新方案。保留必要事务与游标一致性，避免把所有并发保障误当成 E 逻辑。当前只创建讨论文档，旧实现、旧数据库、用户插件配置均未改动。

## 2026-09-15 · 按使用动作收敛为三个工具入口

- 发生：Agent 初稿从旧接口删减得到七个工具，用户追问必要性，并提出 `find_run`、`get_message_detail`、`delete_run`。
- 分析：初稿沿用了搜索、列举、Run 阅读和摘要维护的旧分工，尚未证明它们都需要单独暴露。定位经历可以支持关键词与 ID 两种方式，常规摘要属于后台职责。折叠能力是否保留、是否由 AI 主动调用也应分别决定。
- 改变：工具草案改为三个入口；建议 `find_run` 在搜索时给候选摘要、指定 Run 时给消息预览与详情 ID，保留完整下钻路径。将折叠工具改为只在选择 Agent 主动控制上下文时才讨论的额外能力；具体查询参数及上下文方案仍待确认。

## 2026-09-15 · 确认只积累 Run，退出上下文管理

- 发生：用户明确表示不需要自动折叠、上下文注入及相关操作，整个插件只保留 Run 积累功能。
- 分析：v2 的边界是可查阅的执行归档，不是另一套会话上下文控制器。此前关于折叠责任与目录预算的方案已无须继续讨论；这也使 E 整理以外的第二组复杂状态可以整体退出。此前用户提出的三个归档工具继续作为入口，常规摘要沿用后台职责。
- 改变：主文档收口为记录、摘要、查阅与显式删除，明确模型可见入口限于三个工具定义及调用结果。删除折叠方案、历史目录注入、上下文用量与概览预算、容量保护、维护提示、保留边界及原生压缩固化的设计；主会话上下文交给宿主及专门插件。保留归档恢复与记录完整性保障，并明确删除归档不删除 Pi 会话消息。本次仅更新设计文档。

## 2026-09-15 · 确认第一版搜索范围

- 发生：用户同意第一版先以关键词搜索覆盖摘要和消息正文，并支持目录、时间筛选。
- 分析：当前目标可先用直接查询满足；语义检索是否值得引入，留待实际漏搜证据判断，不预先承担其索引和维护成本。
- 改变：在主文档明确已确认的关键词搜索范围，与尚待确定的查询参数、结果展示和按 ID 定位形式分开。

## 2026-09-15 · 确认从独立空库重新积累

- 发生：Agent 建议继承旧 Run，用户明确选择“空库重新积累”。
- 分析：新版本可以直接采用 Run-only 数据结构，无须为旧 Run、消息编号或 E 承担迁移兼容；空库指 v2 的初始起点，不是每次会话清空，也不是删除旧库的授权。
- 改变：主文档明确 v2 使用独立持久数据库，积累启用后的执行并持续保留；移除旧 Run 迁移与 E 导出计划。实现建议加入新旧库路径与格式隔离，避免误用旧库时写入。

## 2026-09-15 · 确认删除授权边界，收口产品设计

- 发生：用户同意仅在其明确要求或授权清理后删除 Run，授权后 AI 可批量判断与执行，无须逐条确认。
- 分析：归档默认用于持续积累；清理是用户发起或授权的任务，而非 Agent 自主维护。自然语言授权属于工具使用约定，不能把模型自填参数当成程序已验证用户授权的凭据。
- 改变：主文档明确授权范围、批量执行及无逐条确认，并区分工具说明中的使用约定和代码对 ID、状态的确定性检查。产品边界已足够支撑实现，具体参数和返回结构留待实现时处理；本轮仍仅完成设计文档。

## 2026-09-15 · 完成首版并按真实执行修正结束判定

- 发生：用户授权实现后继续推进。已有录制、摘要、工具与终端阅读代码；恢复工作时发现 README 仍停留在设计稿。真实 SDK 新增用例复现了终止工具及工具阶段取消都被误标为结束待确认；首次联网验证脚本又因遗漏 Pi 原生 cwd 后缀而误报。
- 分析：最后一条 assistant 的 stopReason 并不独自决定 Run 是否收束，工具也可直接终止一轮；同时，缺少匹配结果不能算结束证据。验证脚本必须区分宿主原生装配与插件新增内容，失败原件应保留而非覆盖。
- 改变：录制器结合匹配结果、批次终止标记和取消信号判定状态；新增损坏消息的明确诊断与 raw 读取退路。28 项测试、最终真实主请求/摘要和终端阅读已验证；原始证据与工作副本隔离，最终源码哈希对账一致。README 改为试用入口，细节进入 docs/usage.md、docs/design.md、docs/verification.md。保留 Shadow 真实联调及长期运行的未验证边界，旧插件、旧库和用户安装配置不变。

## 2026-09-15 · 从归档用途重新审视 Run 状态

- 发生：安装后，用户询问“已收束”等状态的含义，继而认为多种状态没有明显价值，关注的是记录“有还是没有”及其实际影响。
- 分析：当前搜索、删除和摘要资格主要区分 running 与非 running；失败、中止和正常结束不会改变已保存记录的可查阅性。内部录制边界用于保护活动 Run 和触发摘要，不能据此证明需要向用户暴露完整执行状态分类。
- 改变：记录待讨论的简化方向：对外以已有记录及其内容为中心，内部保留必要的录制中标记；执行结果由摘要和原文说明。本次仅保存反馈与候选方案，尚未删除状态、修改数据库或变更已安装代码。

## 2026-09-15 · 确认并实施无状态归档

## 2026-09-15 · 实际工具试用补齐错误阅读

## 2026-09-15 · 以对话调用卡片呈现参数与精简结果

## 2026-09-15 · 摘要直连补 opencode 会话路由头

- 发生：用户指出摘要未生成，怀疑 glm-5.3-flash 摘要有问题。实际未生成的原因是 `registry.complete` 直连旁路：插件摘要请求未带 opencode 端点要求的 `x-opencode-session` 路由头，网关返回 400 MissingSessionID，而错误被包装成 "Request was aborted"，失败信息不可读。
- 分析：主 agent 流经过 attribution 管线自动补头，扩展直连同一注册表时不会。修的表面是错误包装，根因是直连路径缺 provider 特定头。
- 改变：src/summary.ts 新增 `providerSessionHeaders`（镜像 pi getSessionHeaders 的 opencode 判定：provider 为 opencode/opencode-go 或 host 为 opencode.ai 时补 `x-opencode-session` + `x-opencode-client`），complete 调用带上该头；`validateSummary` 区分 stopReason=error 并透出真实 errorMessage。41 项测试；隔离副本 runs.sqlite + 真实 opencode-go/glm-5.3-flash 端到端验证，原失败 Run 的摘要成功生成落库。

## 2026-09-19 · find_run 增加 OR 与双引号短语

- 发生：用户指出 find_run 不支持类似 rg 的多关键词语法。随后用 r639 验证：约 46 次 find_run、约 25 个近义词全库扫描，真正有用的是「我的想法是」「不认可」和摘要里的「用户纠正」。用户确认方案并要求发新版本。
- 分析：缺 OR 把一组同义词逼成多遍扫描。完整正则会改变字面量默认、提高误写成本。空白 AND 仍然有用。排除词在该次检索里没有独立价值。
- 改变：保留空白 AND 字面量；仅增加大写 `OR` 与双引号短语。命中仍要求某一子句落在同一文本块。解析集中在 src/query.ts，摘要 SQL 与正文扫描共用。不上正则、不加排除词、不加 `|`。

## 2026-09-22 · find_run 描述改为先说何时该查

- 发生：用户在实际使用中发现说「你之前怎么样」时 Agent 不会第一时间调用 find_run，怀疑不是行为问题而是工具没说清楚。核对 git 历史，描述从初版到现在只增补过查询语法，从未写过用途或触发条件。
- 分析：约 90 词里只有开头 14 词说这个工具是什么，其余是查询语法与结果口径，只在决定要用之后才起作用。扩展不注入 guidance，描述是唯一的触发面。四处具体缺口：没有告诉模型上下文装不下更早的执行，所以它以为「之前」就在眼前；第一句只有 `archived Runs` 这个项目术语，没有用户实际会说的指代词；`History is evidence...` 与排除项排在用途之前，读起来像劝退；邻居 `search_context` 的描述里有 "historical messages" 和 "Use to ..." 从句，抢同一批词却是另一个范围。
- 改变：顶层描述改为先说明模型看不见哪部分记忆、覆盖到更早的会话与本会话已滚出上下文的轮次，再给出触发情形（用户指代先前工作、问做过什么、自己正要凭印象作答），免责声明移到末尾。查询语法、分页语义与排除项下沉到 `query`，`scope` 与 find_run 的 `id` 补齐字段说明。行为、参数与产品边界不变，不引入 guidance 注入。改完做了 18 次真实调用对照，触发率没测出差异：裸会话里两臂都是 18/18 首个动作就调 `find_run`，用户报告的情形没能在这些条件下复现，只测到首页未命中后新描述 3/3 会再查一次、旧描述 3/3 转为凭上下文作答。本次只能证明没有回退，不当作触发率提升的证据。
